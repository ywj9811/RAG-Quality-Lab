# 캐시와 Redis 개념

> 이 문서는 지식베이스 주제다. 이 문서를 근거로 답하는 시스템이 Redis를 사용한다는 뜻은 아니다.

## 핵심 개념

캐시(cache)는 **비용이 큰 작업의 결과를 가까운 곳에 잠시 저장해 두고 재사용**하는 기법이다. DB 조회, 외부 API 호출, 복잡한 계산처럼 느리거나 비싼 작업의 결과를 메모리 같은 빠른 저장소에 보관해, 같은 요청이 다시 오면 원래 작업을 반복하지 않는다.

캐시를 판단하는 기본 지표는 **적중률(hit ratio)**이다.

- **캐시 적중(hit)**: 찾는 값이 캐시에 있어서 바로 돌려준 경우
- **캐시 실패(miss)**: 캐시에 없어서 원래 저장소에서 가져와야 하는 경우
- 적중률 = 적중 수 ÷ 전체 조회 수

캐시는 자주 읽히고, 잘 바뀌지 않으며, 원본을 가져오는 비용이 큰 데이터에 효과적이다. 반대로 매번 바뀌는 데이터나 한 번만 읽히는 데이터에는 효과가 적고, 오히려 오래된 값을 보여주는 문제만 생길 수 있다.

## 캐시의 위치

- **로컬 캐시(인메모리 캐시)**: 애플리케이션 프로세스 메모리 안에 둔다(예: Caffeine). 가장 빠르지만, 서버가 여러 대면 서버마다 다른 값을 가질 수 있고 재시작하면 사라진다.
- **분산 캐시(원격 캐시)**: 별도 캐시 서버에 둔다(예: Redis). 여러 서버가 같은 값을 공유하지만, 네트워크 왕복 비용이 든다.
- 두 가지를 겹쳐 쓰는 다단계 캐시도 있다. 이때는 계층 간 값이 어긋나는 문제를 함께 관리해야 한다.

## 캐시 전략

데이터를 캐시와 원본 저장소에 언제 읽고 쓰는지에 따라 전략이 나뉜다.

**Cache-Aside (Lazy Loading)**: 가장 흔한 방식이다.
1. 애플리케이션이 먼저 캐시를 조회한다.
2. 없으면 DB에서 읽고, 그 결과를 캐시에 넣은 뒤 반환한다.
3. 데이터를 수정할 때는 DB를 고치고 캐시 항목을 삭제(무효화)한다.

필요한 데이터만 캐시에 올라간다는 장점이 있고, 처음 조회할 때는 항상 캐시 실패가 난다는 단점이 있다.

**Read-Through**: 애플리케이션은 캐시만 조회하고, 캐시 계층이 실패 시 원본을 대신 읽어 채운다. 흐름은 Cache-Aside와 비슷하지만 원본 조회 책임이 캐시 쪽에 있다.

**Write-Through**: 쓰기 요청을 캐시와 원본에 **동시에(같은 흐름 안에서)** 반영한다. 캐시가 항상 최신이지만, 쓰기 지연이 늘고 읽히지 않을 데이터도 캐시에 쌓인다.

**Write-Behind (Write-Back)**: 캐시에 먼저 쓰고, 원본 반영은 나중에 모아서 비동기로 한다. 쓰기는 빠르지만, 원본에 반영되기 전에 캐시가 사라지면 데이터가 유실될 위험이 있다.

## TTL과 무효화

캐시의 가장 어려운 문제는 **원본이 바뀌었을 때 캐시를 어떻게 맞출 것인가**다.

- **TTL(Time To Live)**: 항목마다 유효 시간을 정해 시간이 지나면 자동으로 만료시킨다. 일정 시간 동안은 오래된 값을 허용하는 대신 구현이 단순하다. 데이터가 얼마나 오래된 상태까지 허용되는지를 기준으로 TTL을 정한다.
- **명시적 무효화**: 데이터를 수정하거나 삭제할 때 관련 캐시 항목을 삭제한다. 수정 시 캐시 값을 직접 덮어쓰기보다 삭제하는 방식이, 동시 요청으로 오래된 값이 다시 쓰이는 문제를 줄이는 데 보통 더 안전하다.
- **둘의 조합**: 명시적 무효화를 기본으로 하고, 무효화를 놓쳤을 때를 대비해 TTL을 함께 둔다.

**캐시 스탬피드(cache stampede)**: 인기 있는 항목이 만료되는 순간 많은 요청이 동시에 원본으로 몰리는 현상이다. 만료 시각에 무작위 편차를 주거나, 한 요청만 원본을 읽도록 잠금을 두거나, 만료 전에 미리 갱신하는 방법으로 완화한다.

**메모리 한도와 축출(eviction)**: 캐시 저장소가 가득 차면 일부 항목을 내보내야 한다. 대표 정책으로 LRU(가장 오래 사용하지 않은 것부터), LFU(가장 적게 사용한 것부터)가 있다.

## Spring Cache 추상화

Spring은 캐시 구현체와 무관하게 쓸 수 있는 **캐시 추상화**를 제공한다. 설정 클래스에 `@EnableCaching`을 붙이고, 메서드에 애너테이션을 단다.

| 애너테이션 | 동작 |
|---|---|
| `@Cacheable("books")` | 캐시에 값이 있으면 메서드를 실행하지 않고 캐시 값을 반환. 없으면 실행 후 결과를 저장 |
| `@CachePut("books")` | 항상 메서드를 실행하고 결과로 캐시를 갱신 |
| `@CacheEvict("books")` | 캐시 항목 삭제. `allEntries = true`면 해당 캐시 전체 삭제 |
| `@Caching` | 여러 캐시 애너테이션을 묶음 |

- 캐시 키는 기본적으로 메서드 파라미터로 만들어지며, `key = "#id"`처럼 SpEL로 지정할 수 있다.
- `condition`(실행 전 조건), `unless`(결과를 보고 저장 제외) 속성으로 캐시 여부를 조절한다.
- 실제 저장소는 `CacheManager` 구현으로 결정된다. Spring Boot는 클래스패스에 있는 라이브러리(Caffeine, Redis 등)를 보고 자동으로 구성한다.
- `@Transactional`과 마찬가지로 **프록시 기반**이므로, 같은 클래스 안에서 자기 메서드를 호출하면 캐시가 적용되지 않는다.
- 캐시에 저장되는 객체는 변경되지 않는(불변) 형태가 안전하다. 캐시에서 꺼낸 객체를 수정하면 로컬 캐시에서는 캐시 값 자체가 바뀌어 버릴 수 있다.

## Redis 개념

Redis는 데이터를 메모리에 저장하는 **키-값 저장소**로, 캐시 용도로 널리 쓰인다. 값으로 단순 문자열뿐 아니라 여러 자료구조를 지원한다.

| 자료구조 | 특징과 쓰임 |
|---|---|
| String | 가장 기본. 문자열, 숫자 카운터, 직렬화된 객체 |
| Hash | 필드-값 묶음. 객체의 일부 필드만 읽고 쓰기 |
| List | 순서 있는 목록. 양쪽 끝에서 넣고 빼기 |
| Set | 중복 없는 집합. 태그, 방문자 집합 |
| Sorted Set | 점수로 정렬된 집합. 순위표 |

- 키마다 만료 시간(TTL)을 지정할 수 있다(`EXPIRE`, `SET` 명령의 `EX` 옵션 등).
- 명령 실행은 기본적으로 하나의 스레드에서 차례로 처리되므로, 개별 명령은 원자적으로 실행된다. 그래서 `INCR` 같은 명령으로 경쟁 상태 없이 카운터를 올릴 수 있다. 다만 오래 걸리는 명령(큰 키 전체 조회 등)은 다른 요청 전체를 지연시킨다.
- 메모리 저장소이지만 스냅샷(RDB)이나 명령 로그(AOF) 방식으로 디스크에 영속화할 수 있다. 캐시 용도라면 영속화보다 원본 DB에서 다시 채울 수 있는지가 더 중요하다.
- 메모리 한도(`maxmemory`)와 축출 정책(예: LRU 계열)을 설정할 수 있다.

## 예시

이 문서를 위해 작성한 예시다.

```java
@Configuration
@EnableCaching
class CacheConfig { }

@Service
class ProductService {
    private final ProductRepository products;

    ProductService(ProductRepository products) { this.products = products; }

    @Cacheable(cacheNames = "product", key = "#id")
    public ProductView find(long id) {
        return ProductView.from(products.findById(id).orElseThrow());
    }

    @CacheEvict(cacheNames = "product", key = "#id")
    @Transactional
    public void changePrice(long id, long price) {
        products.findById(id).orElseThrow().changePrice(price);
    }
}
```

## 자주 하는 실수

- 무효화 계획 없이 캐시를 도입해 오래된 값을 계속 보여주는 것.
- 사용자별로 달라야 하는 데이터를 사용자 구분 없는 키로 캐시해 다른 사람의 데이터가 노출되는 것.
- 같은 클래스 안에서 호출해 `@Cacheable`이 동작하지 않는 것.
- 캐시를 유일한 저장소처럼 써서, 캐시가 비면 데이터가 사라지는 구조를 만드는 것.
- 측정 없이 캐시를 넣어 복잡도만 늘리는 것. 먼저 느린 지점을 확인한다.

## 답변 가능 범위

- 캐시의 목적, 적중률, 캐시가 효과적인 데이터의 조건
- 로컬 캐시와 분산 캐시의 차이
- Cache-Aside, Read-Through, Write-Through, Write-Behind 전략의 차이
- TTL, 명시적 무효화, 캐시 스탬피드, 축출 정책
- Spring Cache 애너테이션의 동작과 프록시 제약
- Redis의 기본 자료구조, TTL, 단일 스레드 명령 처리, 영속화 방식 개요

## 답변 불가 범위

- Redis 클러스터, 센티널 구성과 운영
- Redis 영속화 튜닝과 장애 복구 절차
- Redis 모듈(검색, JSON 등)과 스트림의 상세 사용법
- CDN과 HTTP 캐시 헤더의 상세 설정
