# 관계형 DB 인덱스

## 핵심 개념

인덱스는 테이블의 특정 컬럼 값을 정렬된 구조로 따로 저장해, 원하는 행을 빨리 찾을 수 있게 하는 자료구조다. 책 뒤의 색인과 비슷하다. 인덱스가 없으면 DB는 조건에 맞는 행을 찾기 위해 테이블 전체를 읽어야 한다(전체 스캔, full table scan).

인덱스에는 대가가 있다.

- **쓰기 비용 증가**: INSERT, UPDATE, DELETE 때마다 인덱스도 함께 고쳐야 한다. 인덱스가 많을수록 쓰기가 느려진다.
- **저장 공간 사용**: 인덱스도 디스크와 메모리를 차지한다.
- **항상 쓰이지는 않음**: DB의 쿼리 플래너(옵티마이저)가 비용을 계산해서 인덱스를 쓰는 것이 더 비싸다고 판단하면 전체 스캔을 선택한다.

그래서 인덱스는 "모든 컬럼에" 만드는 것이 아니라, **자주 실행되는 조회 조건과 정렬 패턴**에 맞춰 만든다.

## B-tree 인덱스의 원리

관계형 DB에서 기본으로 쓰이는 인덱스는 **B-tree**(정확히는 B+tree 계열)다. PostgreSQL에서 `CREATE INDEX`를 종류 지정 없이 실행하면 B-tree가 만들어진다.

- 값이 정렬된 상태로 균형 잡힌 트리에 저장된다. 루트에서 잎(leaf)까지의 깊이가 모두 같아, 데이터가 많아져도 찾는 데 필요한 단계가 천천히(로그 규모로) 늘어난다.
- 잎 노드에는 값과 실제 행의 위치가 들어 있고, 잎끼리 순서대로 연결되어 있어 범위 조회에 유리하다.
- 그래서 B-tree는 같음(`=`), 범위(`<`, `<=`, `>`, `>=`, `BETWEEN`), 정렬(`ORDER BY`), 앞부분이 고정된 문자열 패턴(`LIKE 'abc%'`)에 쓸 수 있다.

PostgreSQL에는 B-tree 외에도 Hash(같음 비교 전용), GIN(배열, JSONB, 전문 검색), GiST·SP-GiST(공간 데이터, 범위 타입 등), BRIN(물리적으로 정렬된 매우 큰 테이블) 인덱스가 있다.

## 복합 인덱스와 컬럼 순서

여러 컬럼을 묶은 인덱스를 **복합 인덱스(composite index)**라고 한다. 복합 인덱스는 **앞 컬럼부터 순서대로 정렬**되어 있다는 점이 핵심이다. 전화번호부가 성으로 먼저 정렬되고, 같은 성 안에서 이름으로 정렬된 것과 같다.

`(status, created_at)` 순서의 인덱스가 있을 때:

| 조건 | 인덱스 활용 |
|---|---|
| `WHERE status = 'PAID'` | 잘 활용됨 (첫 컬럼 조건) |
| `WHERE status = 'PAID' AND created_at >= '2026-11-01'` | 잘 활용됨 |
| `WHERE status = 'PAID' ORDER BY created_at DESC` | 정렬까지 인덱스로 처리 가능 |
| `WHERE created_at >= '2026-11-01'` (status 조건 없음) | 효율적으로 활용하기 어려움 |

컬럼 순서를 정하는 일반적인 기준은 다음과 같다.

- **같음(`=`) 조건 컬럼을 앞에**, 범위 조건 컬럼을 뒤에 둔다. 범위 조건 뒤에 오는 컬럼은 탐색 범위를 좁히는 데 거의 도움이 되지 않는다.
- 가장 자주 쓰이는 조회 패턴을 기준으로 정한다.
- 정렬 컬럼까지 포함하면 별도 정렬 작업을 없앨 수 있다.

## 선택도(Selectivity)

선택도는 조건이 전체 행 중 얼마나 적은 비율을 골라내는지를 나타낸다. 고르는 행이 적을수록 "선택도가 높다"고 말한다.

- 사용자 ID, 이메일처럼 값이 거의 겹치지 않는 컬럼은 선택도가 높아 인덱스 효과가 크다.
- 성별, 삭제 여부처럼 값의 종류가 몇 개 안 되는 컬럼에 단독 인덱스를 만들면, 조건이 전체의 큰 비율을 차지할 때 DB가 인덱스를 쓰지 않는 경우가 많다.
- 다만 특정 값이 아주 드문 경우(예: 전체의 1%만 `status = 'FAILED'`)에는 그 값을 찾는 조회에 인덱스가 효과적일 수 있다. 이럴 때는 **부분 인덱스**가 유용하다.

DB는 테이블 통계(값 분포)를 바탕으로 선택도를 추정한다. PostgreSQL에서는 `ANALYZE`가 통계를 갱신하며, 자동 vacuum 과정에서도 주기적으로 실행된다.

## 커버링 인덱스와 부분 인덱스

- **커버링 인덱스**: 쿼리에 필요한 컬럼이 모두 인덱스 안에 있으면, 테이블 본체를 읽지 않고 인덱스만으로 결과를 만들 수 있다. PostgreSQL에서는 이를 Index Only Scan이라고 하며, `INCLUDE` 절로 검색 키가 아닌 컬럼을 인덱스에 추가로 담을 수 있다. 단, PostgreSQL의 Index Only Scan은 테이블 페이지가 모두 보이는 상태(visibility map)로 표시되어 있어야 효과가 크다.
- **부분 인덱스**: `WHERE` 조건을 만족하는 행만 인덱스에 넣는다. 예: `CREATE INDEX ON documents (uploaded_at) WHERE deleted_at IS NULL`. 인덱스가 작아지고, 해당 조건으로 조회할 때만 쓰인다.
- **고유 인덱스**: `UNIQUE` 제약조건을 만들면 고유 인덱스가 함께 만들어져 중복 값을 막는다.

## 인덱스가 쓰이지 않는 경우

인덱스가 있어도 다음 경우에는 쓰이지 않거나 효과가 떨어진다.

- **컬럼을 함수나 연산으로 가공**한 조건: `WHERE lower(email) = 'a@b.com'`, `WHERE created_at + interval '1 day' > now()`. 가공된 값으로 찾으려면 같은 식으로 **표현식 인덱스**(`CREATE INDEX ON users (lower(email))`)를 만들거나, 컬럼을 가공하지 않는 형태로 조건을 바꾼다.
- **앞부분이 고정되지 않은 LIKE**: `LIKE '%abc'`, `LIKE '%abc%'`는 B-tree로 찾기 어렵다. 전문 검색이나 trigram(pg_trgm) GIN 인덱스를 검토한다.
- **타입 불일치**: 문자열 컬럼을 숫자와 비교하는 등 암묵적 형변환이 일어나는 경우.
- **복합 인덱스의 첫 컬럼 조건이 없는 경우**.
- **조건이 너무 많은 행을 고르는 경우**: 플래너가 전체 스캔이 더 싸다고 판단한다.
- **OR 조건**: 각 조건 컬럼에 맞는 인덱스가 없으면 전체 스캔이 될 수 있다.

## EXPLAIN으로 실행 계획 읽기

쿼리가 인덱스를 쓰는지는 추측하지 말고 실행 계획으로 확인한다.

- `EXPLAIN 쿼리`: 플래너가 선택한 계획과 추정 비용, 추정 행 수를 보여준다. 쿼리는 실행하지 않는다.
- `EXPLAIN ANALYZE 쿼리`: 쿼리를 **실제로 실행**하고 실제 소요 시간과 실제 행 수를 함께 보여준다. 데이터를 바꾸는 쿼리에 쓰면 실제로 변경되므로, 트랜잭션 안에서 실행하고 롤백하는 식으로 주의한다.

PostgreSQL 실행 계획에서 자주 보는 노드는 다음과 같다.

| 노드 | 의미 |
|---|---|
| Seq Scan | 테이블 전체를 순서대로 읽음 |
| Index Scan | 인덱스로 위치를 찾은 뒤 테이블에서 행을 읽음 |
| Index Only Scan | 인덱스만으로 결과를 만듦 |
| Bitmap Index Scan / Bitmap Heap Scan | 인덱스로 위치 목록을 만든 뒤 테이블을 모아서 읽음 |

추정 행 수와 실제 행 수가 크게 다르면 통계가 오래됐을 가능성이 있다.

## 예시

이 문서를 위해 작성한 예시다.

```sql
-- 자주 쓰는 조회: 특정 회원의 최근 주문
SELECT id, total, created_at
FROM orders
WHERE member_id = 42
ORDER BY created_at DESC
LIMIT 20;

-- 같음 조건 컬럼을 앞에, 정렬 컬럼을 뒤에 둔 복합 인덱스
CREATE INDEX idx_orders_member_created ON orders (member_id, created_at DESC);

-- 실제 계획 확인
EXPLAIN ANALYZE
SELECT id, total, created_at FROM orders
WHERE member_id = 42 ORDER BY created_at DESC LIMIT 20;
```

## 자주 하는 실수

- 모든 컬럼에 단독 인덱스를 만드는 것.
- 복합 인덱스의 컬럼 순서를 조회 패턴과 무관하게 정하는 것.
- 인덱스 컬럼을 함수로 감싼 조건을 쓰고 인덱스가 쓰일 것이라고 기대하는 것.
- 실행 계획을 확인하지 않고 인덱스 효과를 추측하는 것.
- 운영 중 큰 테이블에 잠금을 고려하지 않고 인덱스를 만드는 것(PostgreSQL은 `CREATE INDEX CONCURRENTLY`로 쓰기 차단을 줄일 수 있다).
