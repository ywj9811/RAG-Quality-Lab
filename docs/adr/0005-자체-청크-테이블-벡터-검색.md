# ADR-0005: Spring AI VectorStore 대신 자체 `document_chunks` 테이블로 벡터 검색

- 상태: 제안됨 (2026-11-12, 2026-11-12 근거 보강)
- 관련: DOC-03, DOC-04, DOC-05, CHAT-06, EVAL-02, 명세 6·7절

## 배경
Spring AI `PgVectorStore`의 기본 스키마는 다음과 같은 고정 구조다.

```sql
vector_store (id uuid PRIMARY KEY, content text, metadata json, embedding vector(N))
```

문서 ID, 버전, 청크 순번, 위치, 임베딩 모델, 삭제 여부를 모두 `metadata` JSON 하나에 넣어야 한다. 이 프로젝트는 청크를 관계형 데이터처럼 다뤄야 하는 요구사항이 많다.

## 결정 (제안)
- Flyway로 `document_chunks`(`vector(1024)`, HNSW cosine) 테이블을 만든다.
- 검색은 `JdbcTemplate` 네이티브 SQL로 한다. `documents`를 조인하고 `status='READY' AND deleted_at IS NULL`로 거른 뒤 `ORDER BY embedding <=> :q LIMIT :k`로 정렬한다.
- Spring AI는 `EmbeddingModel`(Ollama)과 `ChatModel`(Gemini)만 쓴다. `spring-ai-starter-vector-store-pgvector`는 추가하지 않는다.
- 벡터 값은 `'[…]'::vector` 문자열 변환으로 넘긴다. 새 의존성은 없다(`pgvector-java`가 필요해지면 별도 승인).

## 근거: 요구사항별 비교

| 요구사항 | VectorStore 사용 시 | 자체 테이블 |
|---|---|---|
| READY 상태이고 삭제되지 않은 문서만 검색 (DOC-03/05) | 상태가 `documents`와 `vector_store` 두 곳에 나뉜다. 청크마다 metadata에 상태를 복사하고 변경될 때마다 갱신해야 하며, 하나라도 놓치면 삭제된 문서가 검색된다 | `documents` JOIN으로 거른다. 상태는 한 곳에만 있다 |
| 즉시 검색 제외 + 30일 뒤 물리 삭제 (보존 정책) | `delete`는 바로 지우는 방식뿐이다. soft delete를 하려면 metadata 플래그와 모든 검색에 필터가 필요하다 | `deleted_at` 컬럼 + 부분 인덱스 |
| 무결성 (DOC-04) | JSON 안의 값에는 FK, `UNIQUE(document_id, chunk_index)`, NOT NULL을 걸 수 없다 | DB 제약조건으로 막는다 |
| 평가 재현성 (CHAT-06, EVAL-02) | `retrieval_records`와 원래 청크의 관계를 DB로 표현할 수 없다 | `chunk_id` FK `ON DELETE SET NULL`로 "원본은 삭제, 스냅샷은 보존"을 표현한다 |
| 필터·검색 성능 | metadata가 `json` 타입이고 필터가 JSON path로 변환되어 인덱스 활용이 어렵다. HNSW 탐색 후 필터가 적용되면 결과가 Top-K보다 적을 수 있으며, 이를 보완하는 `hnsw.iterative_scan`/`ef_search`를 쿼리 단위로 지정할 수 없다 | 일반 컬럼 조건, 부분 인덱스, `SET LOCAL`을 직접 제어한다 |
| 스키마 관리 | 자동 생성 시 쓰지 않는 `hstore`, `uuid-ossp` 확장이 생긴다(자동 생성을 끄면 해결되므로 결정적 이유는 아님) | Flyway로 Git에서 버전 관리한다 |

## 트레이드오프 (자체 테이블의 비용)
- 일괄 삽입, 검색 SQL, 결과 매핑을 직접 작성하고 Testcontainers로 테스트해야 한다.
- Spring AI RAG 어드바이저(`QuestionAnswerAdvisor`, `RetrievalAugmentationAdvisor`)는 `VectorStore`가 있어야 쓸 수 있다. 다만 이 프로젝트는 다음 처리를 어차피 직접 해야 해서 어드바이저와 잘 맞지 않는다.
  - LLM 호출 전에 임계값으로 근거 부족을 판정해 거절(무료 한도 절약)
  - 검색 결과 스냅샷 저장
  - 인용 번호 검증
- 다른 벡터 DB로 바꾸기 어렵다. 그러나 PostgreSQL + pgvector는 확정된 결정이므로 실제 손해는 작다.

## 대안
1. **Spring AI PgVectorStore + metadata 필터:** 코드가 적고 프로토타입에 적합하다. 위 비교표의 정합성·무결성 문제로 채택하지 않는다.
2. **자체 테이블 위에 Spring AI `VectorStore` 인터페이스를 직접 구현:** 스키마 통제와 어드바이저 호환을 함께 얻지만 인터페이스에 맞추느라 코드가 늘어난다. 지금은 어드바이저를 쓰지 않아 채택하지 않는다. 나중에 필요해지면 이 방식으로 옮길 수 있다.

## 결과
- 스키마를 DB 마이그레이션으로 완전히 통제한다.
- 검색 계층은 `ChunkSearchPort` 인터페이스 뒤에 두어 대안 2로 옮기기 쉽게 한다.
